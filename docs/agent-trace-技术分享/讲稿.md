## Trace 基础（第 1–4 页，约 2 分 30 秒）

### 第 1 页 · 封面（15 秒）

大家好，我是 Agent Trace 组的曹金羽。今天介绍 agent trace 的基本概念和用途，以及组内在 trace 摄入与存储、失败归因、ARC-AGI-3 / VISTA 三个方向上的工作。

### 第 2 页 · Chat、Trace 与 Memory（45 秒）

这三个概念容易混用，先做区分。

Chat 记录即对话 transcript：系统提示、用户消息、模型回复和工具结果按时间排列的文本序列，也就是模型在上下文窗口中看到的内容。上下文接近上限时，这部分会被压缩或截断。

Memory 指 agent 的长期记忆：从历史执行中提炼出的条目，持久保存，在后续任务开始时注入上下文，例如某个仓库的测试命令或用户偏好。它是经过筛选和改写的摘要，不保留原始过程。

Trace 记录一次运行的执行过程。每次 LLM 调用和工具调用都是一个 span，带起止时间、父子关系、状态、模型名、token 用量和输入输出。chat 记录对应 trace 中 LLM 调用的输入输出部分。目前多数记忆生成工作先把 trace 转成纯文本再处理，父子结构、耗时和状态码在这一步丢失。

### 第 3 页 · Trace 的结构（45 秒）

这一页是一次 code agent 运行的示意数据，任务是修复一个失败的测试。左列是 span 名称，缩进表示父子关系；中间是时间轴；右列是部分 attributes。

根节点是主 agent coder。它调用一次 LLM 后，启动子 agent tester 复现失败；tester 内部依次调用 LLM、运行测试和再次调用 LLM，其中运行测试的 span 状态为 ERROR。之后主 agent 调用 LLM 生成修改、编辑文件并重新运行测试，测试通过。

每个 span 通过 parent\_span\_id 指向父 span，同一次运行的所有 span 共享一个 trace\_id，因此构成一棵树。attributes 中，token 用量等字段按 OTel GenAI 语义约定命名，文件名、退出码等由工具自行记录。从这棵树可以直接读出错误所在的步骤、各步骤的耗时和 token 消耗。存储上，span 是主要的写入和分析单元，trace\_id 是关联键。

### 第 4 页 · Trace 的用途（40 秒）

trace 的主要用途有四类。可观测性：分析延迟由哪些步骤构成，以及各模型的 token 用量和成本。评估：统计某个模型、agent 版本或工具在一段时间内的成功率和延迟分布，或在离线评测中对每一步打分。失败归因：确定失败由哪个 agent 在哪一步引入，后面单独介绍。记忆与回放：从历史 trace 生成记忆，或按步骤恢复运行状态，从断点继续执行。

从查询模式看，单次运行的分析需要按 trace\_id 取出整棵树，统计分析需要跨大量 span 做过滤和聚合；写入是持续追加。整体属于 append-heavy 的 OLAP 负载。

## 组内工作（第 5–6 页，约 1 分 50 秒）

### 第 5 页 · OpenTelemetry：我们用到的部分（50 秒）

trace 的采集和传输使用 OpenTelemetry，简称 OTel。OTel 是 CNCF 的可观测性标准，定义了 trace、metric、log 的数据模型、各语言 SDK 和传输协议 OTLP，最初用于微服务的分布式追踪，即记录一个请求经过多个服务的调用链。GenAI 语义约定在同一数据模型上规定了 LLM 和 agent 调用的属性命名。

我们的链路：agent 侧通过 OTel SDK 埋点，或由 trace-synthesis 回放合成数据，经 OTLP/HTTP 发送到 Collector；Collector 中依次是 receiver、batch processor 和自研的 openGauss exporter，最终写入 openGauss 行存、xstore 列存或 PostgreSQL。

用到的能力有三部分。数据模型：Resource、Scope、Span 三层结构，以及 trace\_id、span\_id、parent\_span\_id。GenAI 语义约定：模型名、token 用量、输入输出消息。Collector 定制：用官方构建工具 OCB 编译包含自研 exporter 的发行版，使用其发送队列实现重试、背压和并行写入，并用 accepted 与 sent 指标做对账。

### 第 6 页 · 存储侧实验（1 分钟）

这一页列出存储侧的五项实验。

摄入对账：验证 trace 从发送到入库不丢失、不重复。数据经 Collector 写入 openGauss，将发送成功的 span 清单与库中数据做集合差，10 个 trace、69 个 span 全部入库，差集为空。

列存写入：50 万个 span 写入 xstore 列存，无丢失；8 路并行写入吞吐约 10,316 行每秒。

查询去重：OTLP 的成功响应只确认当前一跳，客户端重试会产生重复 span；目标引擎的列存不支持主键和唯一约束。因此写入只追加，查询时按 (trace\_id, span\_id) 取最新版本。将查询改为先过滤再去重后，延迟从约 4 秒降到 141 至 257 毫秒。

图查询：把 span 的父子关系存为图的边，用 Cypher 查询，并与列存对比。取整棵 trace 树快 23 倍，取 payload 慢 1.5 倍，因此图只用于关系查询。这组数据来自 debug 构建，只用于比较数量级。

payload 存储：prompt 和 response 等长文本占存储的主要部分。我们对比了同表、拆表、外置等布局，并分析了 3,600 条真实轨迹。同一批轨迹，每次 LLM 调用记录累积的完整上下文时，存储量是只记录增量的 53.15 倍。因此记录粒度需要在建表前确定。

## 失败归因（第 7–9 页，约 2 分 20 秒）

### 第 7 页 · 失败归因：Who&When（40 秒）

失败归因（failure attribution）的问题定义是：多 agent 系统执行任务失败后，根据执行轨迹确定由哪个 agent、在哪一步引入了导致失败的决定性错误。

Who&When 是这一方向的 benchmark，发表于 ICML 2025，包含 184 条人工标注的失败轨迹，任务来自 GAIA 和 AssistantBench。最直接的基线是 All-at-Once：把完整轨迹交给 LLM，一次输出 agent 和步骤，属于 LLM-as-a-judge。同事用 DeepSeek-V4.1-Flash 复现了该基线：在算法生成的 126 例上，agent 级准确率 69.05%，步骤级准确率 21.43%；在人工构造、轨迹更长的子集上，步骤级准确率为 5.17%。步骤级定位明显难于 agent 级。

### 第 8 页 · DAG 回溯：流程示例（60 秒）

同事提出的方法称为 DAG 回溯。这里用一个虚构示例说明流程：任务是计算每人 10 元、10 人的总额，正确答案 100 元，系统最终输出 120 元。

第一步，构图。LLM 读取完整轨迹，标注每一步使用了哪些前序步骤的输出，得到步骤间的依赖图。例如 Step 3 的计算使用了 Step 1 的人数和 Step 2 的单价。

第二步，确定起点。找到失败表现所在的步骤，这里是 Step 5 输出了错误答案。

第三步，回溯。从 Step 5 开始沿依赖边反向遍历，对每个步骤由 LLM 判断两件事：该步骤本身是否引入错误，以及还需要检查哪些上游步骤。Step 5、4、3 本身没有错误，只是使用了错误的上游输出；Step 1 把人数读成 12，本身出错，记为候选。Step 0 和 Step 2 不在回溯路径上，不做检查。

第四步，裁决。有多个候选时由 LLM 选择一个；本例只有一个候选，输出 Step 1，对应的 agent 是 Reader。

### 第 9 页 · DAG 回溯：结果（40 秒）

左侧是对比的两种基线：All-at-Once 一次判断；Step-by-Step 从第一步开始逐步判断，在第一个被判为出错的步骤处停止。

右侧是步骤级准确率。算法生成子集上，两个基线分别为 21.43% 和 34.92%，DAG 回溯为 48.41%；人工构造子集上，两个基线为 5.17% 和 17.24%，DAG 回溯为 29.31%。token 消耗是基线的 2.3 到 4.8 倍。

DAG 回溯的每个错误样例都可以归入四类之一：标注步骤在图上不可达、未被回溯到、局部判断错误、裁决选错，可据此定位需要改进的环节。以上为单次运行结果，作者也说明尚不能证明收益稳定。

## ARC-AGI-3 与 VISTA（第 10–15 页，约 4 分 50 秒）

### 第 10 页 · ARC-AGI-3：没有规则的交互式游戏（55 秒）

ARC-AGI-3 是 ARC Prize 基金会发布的交互式推理 benchmark，由回合制抽象游戏组成。左侧是游戏 sb26 第 0 回合的画面，也是模型得到的全部输入：64×64 网格、16 种颜色，以及若干按键和点击动作。环境不提供规则和目标说明，agent 需要自行探索、推断胜利条件，并把得到的规律用于后续关卡。

计分方式为 RHAE：每关得分为人类动作数与 AI 动作数之比的平方，人类基线来自首次接触游戏的玩家。公开集有 25 个游戏、183 关，人类可以完成全部环境。左下角是官网的试玩链接。

右侧是官方榜单，设置为标准 harness、不提供工具。3 月发布时前沿模型均低于 1%；目前最高的 GPT-6 Astra 为 62.7%，Claude Opus 5 为 30.2%。多数模型仍低于 1%，包括我们实验中使用的 DeepSeek-V4.1-Flash 和 GPT-6 Luna。

备注（回答提问用）：榜单分数取自官方榜单的第三方汇总页，截至 2026-10-14，以官网为准。榜单是全部公开游戏的总分，与我们在单个游戏上的实验得分不可直接比较。

### 第 11 页 · VISTA：无损视觉记忆（45 秒）

VISTA 是 MIT 何恺明组 2026 年 10 月发表的工作，核心是一个 harness：每一帧画面都无损保存为图片并在整局中保留，模型通过检索工具按回合号读取任意历史画面和动作记录，并维护两份笔记。系统提示只有 9 行，不提供规则和策略，模型也不能执行代码。

在这个 harness 下，Opus 5.0 的 RHAE 从最小接口下的 40.68 提高到 100，公开集 183 关全部完成，总动作数 7,542，人类首次游玩为 17,135。作者据此认为，模型本身的能力已经足够，限制因素是缺少可随时查阅的无损记录。

备注（回答提问用）：40.68 取自论文摘要；VISTA 博客列出的官方最小接口基线为 30.16，与榜单中 Opus 5 的 30.2% 一致，两处口径不同。作者也说明，模型发布晚于公开游戏，不能排除训练数据中包含这些游戏，泛化能力需要用私有集检验。

### 第 12 页 · VISTA 的 8 个工具与系统提示（45 秒）

左侧是 VISTA 提供的全部 8 个工具。play 执行一个动作，返回本回合的元数据和最后一帧。三个检索工具：inspect 按回合号、帧号和区域读取历史截图并放大；read\_pixels 在指定区域按行列网格采样，返回颜色矩阵，用于精确测量；history 返回逐回合的动作与结果，或本关历次尝试的摘要。两组笔记工具：GUIDE 保存跨关卡的长期结论，WORKING 保存本关草稿，过关时归档并清空。

右侧是系统提示全文。它只规定目标——用尽量少的动作完成游戏，并要求模型持续修正对游戏的理解、每次动作前后说明预期与观察到的变化、把结论写入笔记；不含规则、示例或策略。

另有两项约束：只有 play 会自动返回画面，其余历史信息需要模型按回合号主动查询；运行时的内置工具全部禁用，模型不能读文件或执行代码。

### 第 13 页 · VISTA 的无损游戏记录（40 秒）

这张图是 VISTA 运行时的数据流。左侧是模型的会话上下文，接近上限时进行压缩（compaction）并开启新会话，旧上下文整体丢弃。中间是控制器写入的截图、事件表和两份笔记，在整局中保留，模型可随时通过工具读取。

VISTA 的核心是在文件系统中为 agent 保存一份可随时查询的无损游戏记录。按本次分享的定义，它属于广义的 trace：按回合平铺，只包含游戏本身的信息，读取方是运行中的 agent。

### 第 14 页 · 两层记录：游戏即时数据与执行全量记录（40 秒）

我们在 VISTA 上的工作对应另一层记录。左列是 VISTA 的游戏即时数据；右列是我们实现的执行全量记录，对应 VISTA 的 private 目录，并改为结构化存储。除游戏数据外，它还包括每次 LLM 调用、工具调用、会话段、上下文压缩、ARC 服务请求和原始文件，以 OTel span 树的形式写入数据库。

两者的读取方不同。游戏即时数据由运行中的 agent 读取；执行全量记录供开发者以及评估、优化流程使用，用于评估、失败归因、断点续跑、改进 harness，以及论文所需的实验分析。

### 第 15 页 · 执行全量记录的 OTel 实现（40 秒）

实现上，一局游戏对应一个 trace。VISTA 进程中有两条导出通道：即时数据通道使用较短的批处理间隔，审计通道承载大体积原文。两条通道都经 OTLP 发送到 Collector，由前面介绍的 exporter 写入同一张 events 宽表。

即时数据在运行中需要被 agent 读回，因此加入读屏障：读取前先 flush，并等待相关 span 入库，保证 read-your-writes。审计数据把 private 目录中的原始文件分块归档，可逐字节还原。每次写笔记都生成一个新 span，因此任意步骤的笔记版本都可以精确取回，用于断点续跑：重放前 N 步，逐步核对观测一致后继续执行。

验证结果：500 步回放中，工具返回与文件存储逐字节一致；在 OTLP 异步导出下，每次工具调用的额外延迟约 7 毫秒。

## 小结与问答（第 16–17 页，约 40 秒）

### 第 16 页 · Agent Trace 的关键点（30 秒）

小结页列出四点。第一，trace 是一次运行的结构化执行记录，包含 chat 记录和 memory 中没有的结构、时间和状态信息。第二，OTel 统一了数据模型和传输协议；存储侧是追加写入和时间范围分析，需要处理去重和长 payload。

第三，失败归因中步骤级定位明显难于 agent 级，利用执行依赖结构可以提高步骤级准确率。第四，对 agent 而言，可随时查阅的无损记录会直接影响任务表现；对评估和优化而言，完整的结构化记录是分析依据。
