## 01 · 记录形态｜四种记录的区别

### 第 4 页 · 对话文本、Trace、State 与 Memory：内容与格式

约 55 秒 · 累计 03:40–04:35

这张表回应上一场听众的提问，“典型格式”一行对应上一页的四个框。

对话文本每次调用前重新组装，读取方是模型和用户；trace 只追加，覆盖整个执行过程，供开发、评估、归因和审计读取；state 覆盖当前值或新增快照，供框架继续和恢复执行；memory 跨任务复用，需要修订和撤回，供后续任务中的模型读取。

按 DB 类比，对话文本相当于查询结果集，trace 相当于日志或 WAL，state 相当于数据页或调用栈，memory 相当于物化视图。四者首先按写入方式区分。

【翻页】下一页看四者的重叠和转化。

可能的提问：

- 问：state 和 memory 都是“记住的东西”，怎么区分？
  答：state 属于一次执行，执行结束后可以归档或丢弃；memory 面向以后的任务，需要来源、适用条件和版本，因为它可能过时或出错。
- 问：memory 是 trace 的子集吗？
  答：不一定。记忆可以由 trace 归纳，也可以来自人工或其他来源；从 trace 生成时应保留指向原记录的引用。

## 01 · 记录形态｜四种记录的转化

### 第 5 页 · 重叠、互斥与转化：运行时组装与事后派生

约 130 秒 · 累计 04:35–06:45

上半部分是运行时：每次模型调用前，框架把 state、检索到的 memory 和当前观测组装成本次对话文本，调用后写回 state。下半部分是记录：每一步追加为 trace 的 span，trace 不进入模型输入。所以保存的历史多于某一步模型看到的内容，分析一次决策要还原当时的输入。

对 DB 背景，trace 与 state 的关系接近日志与调用栈：日志记录执行经过，调用栈只保留当前位置，过去的帧要依据日志重建。

从 trace 出发有三条转化。重放：状态写入全部有记录、环境确定时，可以重放得到 state，对应 checkpoint 加 redo。还原：保存了完整输入或裁剪规则时，可以还原当次对话文本。提炼：归纳出 memory，这一步有损，需要保留来源 span 和版本，相当于物化视图。

span 关系、时延、重试、被裁剪的旧消息和 state 的旧值只在 trace 中。记录约定还决定数据量：按本组对同一批 Open-SWE 轨迹的统计，每次调用存完整上下文比只存新增消息大 53.15 倍。

后面的 VISTA 中，动作与观测记录是 trace，WORKING 是 state，GUIDE 和 mechanisms 是 memory。

可能的提问：

- 问：有了 state 快照，为什么还要 trace？
  答：快照记录当前值，不记录值的变化过程。排查、归因、审计和重新提炼经验都需要过程记录；快照用于恢复，trace 用于解释过程。
- 问：为什么不把每次完整请求都存下来？
  答：可以存，代价是大量重复内容：同一批 Open-SWE 样本按完整上下文与增量消息两种约定计算，体积相差 53.15 倍。增量存储省空间，但需要能重建当次输入。

## 02 · 存储与管理｜存储引擎

### 第 8 页 · 三个引擎：与实验相关的存储特性

约 90 秒 · 累计 10:00–11:30

两组实验用到三个引擎，这一页只列与实验相关的特性。

openGauss 是 PG 系行存，大家比较熟悉。与实验有关的是 TOAST：一行超过约 2 KiB 时，大字段压缩后另存，主行只留指针。

XStore 是 GaussDB 系行存，SQL 与 openGauss 同源，实验复用了 openGauss 的脚本。它不使用 TOAST，大字段不压缩，直接留在主表 heap 中。兼容上有三处要改写：空字符串按 NULL 处理，不支持 FILTER 聚合写法，分页游标要补一个时间下界才能走索引。

ClickHouse 是 MergeTree 列存，数据按列压缩，查询只读用到的列。它没有行级更新，改状态要用 mutation；JOIN 先把整张右表读进哈希表。part、merge 和 JSON 子列对两组实验的结果影响较大，下一页单独介绍。

【翻页】下一页展开 ClickHouse 的两个机制。

### 第 9 页 · ClickHouse：part 与 merge、JSON 子列

约 105 秒 · 累计 11:30–13:15

左边是 MergeTree 的写入单位。每次 INSERT 生成一个 part，part 写成后不再修改，各列分别压缩存放。后台 merge 选出相邻的小 part，读出数据重新写成一个新 part，完成后原子替换旧 part。查询要逐个打开 part 定位数据，所以 part 越多，固定开销越大。没有行级更新，改一行要用 mutation 重写这一行所在的 part。

右边是 JSON 类型。一个 JSON 列在每个 part 内按路径拆成子列：建表时可以用 type hint 声明路径和类型；其余路径自动建为动态子列，实验设置每个 part 最多 32 条；超过上限的路径放进共享区，多条路径合存。按路径查询只读对应的子列，不解析整段文本。

路径的分配在每个 part 内单独进行。merge 写新 part 时，按各路径的非空值数重新选出动态子列，原来在共享区的高频路径可以升为单独子列。代价有两项：返回完整文档时要汇集全部子列再重组；子列和路径元数据增加写入工作和空间。

## 02 · 存储与管理｜长载荷布局实验

### 第 11 页 · 长载荷布局实验：四种布局

约 190 秒 · 累计 15:35–18:45

长载荷实验比较四种布局，图中绿色是含载荷的表，蓝色是不含载荷的表。same_table 把载荷和普通列放在同一张 events 表。separate 把载荷拆到 event_payloads 表，看详情时按 event_id 连接。full_core 保留完整的 events_full 表，再双写一份不含载荷的 events_core，列表读 events_core，详情读 events_full。

asset_ref 在库内有两张表：events_analytics 存普通列和 asset_id 引用；assets 是对象目录，每个对象一行，记录状态、长度、SHA-256 和文件位置。虚线以下的对象文件在库外，按内容寻址。写入时先在 assets 登记 pending，再发布文件，然后把状态改为 available，最后写事件行；读取时按引用查目录，核对状态和校验值后再读文件。

assets 单独成表，是为了记录对象自己的状态和生命周期：对象可能已发布但尚未绑定事件，也可能需要失败清理或删除。正常写入先完成目录和文件发布，再追加事件。其他三种布局在本实验中同样只做 INSERT；asset_ref 的额外代价来自每个对象的同步状态 mutation，分表本身并未消除这项开销。实验没有比较把目录状态合入事件表的外置变体，也没有测内容去重收益。

separate 和 full_core 都是两表追加：行存在同一事务中写入；ClickHouse 分别 INSERT，实验等待所有目标可见后继续。这是实验同步屏障，生产异步采集还需要单独设计跨表可见性。

载荷共 160 条，分 64 KiB、512 KiB 和 2 MiB 三档；另做等总字节对照，同样 80 MiB，分别切成 40 个大对象或 1,280 个小对象。四种布局返回的字节相同，逐条核对 SHA-256。

### 第 12 页 · 长载荷布局实验：各场景的推荐布局

约 185 秒 · 累计 18:45–21:50

表中每格是该场景下的推荐布局，库内布局指 asset_ref 以外的三种。写入在三个引擎上都是 same_table 最快，其他布局多了写入步骤。ClickHouse 的 asset_ref 最慢，因为每个对象改一次目录状态，就是一次同步 mutation。

空间要看引擎是否在库内压缩。openGauss 用 TOAST 压缩，ClickHouse 按列用 ZSTD 压缩，载荷外置后按原始字节存放，总空间反而变大，右侧卡片是 2.88 倍和 6.92 倍；XStore 不压缩，外置后为 0.79 倍。

列表与预览不读载荷。openGauss 走索引，四种布局都只读 256 行。ClickHouse 不读载荷列，但载荷列让每个 granule 覆盖的行更少，同表反而读得更少，例如中间页 same_table 读 2.4 万行，其他布局读 3.9 万行。XStore 的载荷留在主表 heap，中间页回表 1.4 万行时 same_table 为 125 ms，窄表约 58 ms。

详情与 Trace，行存上库内布局最快。ClickHouse 的 separate 要先把整张 event_payloads 读进哈希表，完整 Trace 读 5.7 万行，same_table 只读 5,400 行，所以应当避开。

批量恢复看对象数，与总字节无关：同样 80 MiB，40 个大对象时外置最快，1,280 个小对象时外置最慢，因为每个对象都要查一次目录、读一次文件。

最下面一条是 ClickHouse 的 part 状态。按上一页的机制，part 越多定位开销越大：190 个 part 时列表第一页为 38 到 45 ms，合并成一个 part 后为 12 到 14 ms，约 3 倍；同一状态下四种布局只差 1.1 到 1.2 倍。所以要先控制 part 数，再选布局。

## 02 · 存储与管理｜选型推论

### 第 13 页 · 选型推论：按引擎与访问需求

## 03 · VISTA 实例｜Benchmark：ARC-AGI-3

### 第 14 页 · ARC-AGI-3：定位、规模与计分

约 100 秒 · 累计 23:40–25:20

ARC-AGI 是广受关注的通用智能推理评测系列，ARC-AGI-3 是其交互式版本。ARC Prize 2026 为这一赛道设置 85 万美元奖金，其中 70 万美元大奖要求达到 100% 得分，并公开代码和方法。它衡量模型在陌生环境中探索、建模和持续学习的效率。

每个游戏是 64×64、16 色的网格画面，不给规则和目标，需要探索并推断胜利条件，再把规律迁移到后续关卡。公开集有 25 个游戏、183 关，半私有集与完全私有集各有 55 个游戏。

各游戏、各关的难度不同，得分用首次游玩者的动作数作基线，衡量是否过关以及动作效率。只计算改变环境的动作，单关效率按规则转换为分数；后续关卡的权重更高，先在游戏内加权，再对各游戏等权平均。因此总分同时反映过关范围和相对人类的动作效率。

官方榜单使用半私有集和统一系统提示，不提供工具和 harness，每关动作上限为人类中位数的 5 倍；带 harness 的结果另列社区榜单。

## 03 · VISTA 实例｜已有框架：VISTA

### 第 16 页 · VISTA：无损视觉记录与 8 个工具

约 125 秒 · 累计 27:30–29:35

VISTA 来自 2026 年的论文，第一作者 Qiushi Han，最后一位作者是何恺明。何恺明提出了 ResNet，也是 Mask R-CNN、MoCo 和 MAE 的第一作者，ResNet 论文是本世纪被引用最多的论文之一。

VISTA 是 ARC-AGI-3 上的执行框架，核心做法是把每帧画面无损保存并整局保留。表中 8 个工具：play 执行 ACTION1 到 7 或 RESET，返回状态元数据和本回合最后一帧；inspect 一次取 1 到 16 个视图，返回放大的历史截图，read_pixels 按网格返回颜色符号矩阵；history 按回合区间查询动作与结果，或各次尝试的概况。两份笔记各有一对读写工具：GUIDE 至多 64 KB，整局保留较稳定的游戏理解；WORKING 至多 16 KB，记录当前状态、已试方案和计划，过关时归档清空。

系统提示只有 9 行，要求用尽量少的动作完成游戏，行动前说明预期、行动后说明变化；不给规则和策略，禁用内置工具，模型不能读文件或执行代码；除 play 外，历史都要模型主动查询。对照第 5 页，截图和动作记录是 trace，WORKING 是 state，GUIDE 是 memory。

【翻页】一局常有上千个动作，会超出上下文。

### 第 17 页 · 上下文会压缩，历史和笔记继续保留

约 25 秒 · 累计 29:35–30:00

接近上下文上限时，模型先更新 WORKING，新会话从当前观测和笔记开始，需要时再检索历史。截图、动作记录和两份笔记整局保留，不受压缩影响；笔记由模型编写，保存后仍需验证。

【翻页】本地在上游之上做了两层扩展。

## 03 · VISTA 实例｜三层结构

### 第 18 页 · VISTA 的三层：上游能力、trace 接入、经验辅助

约 65 秒 · 累计 30:00–31:05

第一层是上游 VISTA 的工具、视觉记录和笔记。第二层是本地 trace 接入：把动作、观测、模型与工具调用、笔记版本写成同一局的 trace，经 OTel 写入 PostgreSQL；这一层有三种读取：游戏读取是运行中读截图、动作和笔记，要求写后可读；审计读取供开发和评估使用，要求结束时完整核对；恢复读取已确认的动作前缀。工具接口保持上游原契约。

第三层是 11 项 aids：框架整理观测、检索和统计，模型编写带来源的规则和交接。第二层用固定回放验证返回内容一致，第三层用行为记录说明经验被采用，第 24 页分别比较两种配置的整体结果。

【翻页】先看第二层的写入与读取。

可能的提问：

- 问：文件已经能保存和回看，为什么改用数据库？
  答：统一成 trace 后可以按运行、回合、版本关联查询，支持断点恢复，并把模型调用等审计信息放进同一结构。代价是异步链路需要可见性确认（第 20 页）；固定回放中 pg/otlp 相对文件约多 7 ms／调用，返回内容逐字节一致。

## 03 · VISTA 实例｜Trace 版改造

### 第 19 页 · VISTA Trace 版：写入与读取路径

约 50 秒 · 累计 31:05–31:55

写入时，控制器的动作、截图和笔记修改经 OTel 分游戏数据和审计两个通道导出，通过 Collector 写入 PostgreSQL 的 events 表，并建立读取索引。一局对应一个 trace，所有内容只追加，笔记修改也是新版本，当前笔记取 agent.seq 最大的一条，即由日志推导 state。读取时由适配层按回合、顺序和版本取数据，模型看到的工具接口不变。

【翻页】OTel 导出是异步的，下一页说明读屏障和恢复。

### 第 20 页 · 读屏障与恢复：从已确认的记录继续

约 70 秒 · 累计 31:55–33:05

读屏障解决写后可读：模型刚执行的动作，下一次查询时可能还没入库。工具返回历史前，先记下待确认的 span_id，对游戏数据通道 force_flush，再查询数据库确认这些记录都可见；超时明确报错，不返回不完整的历史。读到的记录按 agent.seq 排序、按 span_id 去重。对 DB 背景，这相当于在异步链路上为游戏读取实现读己之写。

恢复从已确认的动作继续同一局：读取断点前已确认的动作前缀和当时的笔记版本，在新环境中重放并逐步比较观测，一致后启动新会话。恢复点由运行 ID、确认动作序号、笔记版本和恢复来源确定；它要求环境确定、配置一致，新运行延续动作计数和预算。

【翻页】第三层是 11 项 aids。

可能的提问：

- 问：等待会不会很慢？
  答：固定回放（ls20，500 步、735 次工具调用）中，pg/otlp 相对文件存储平均多约 7 ms／调用，三种存储返回的文字和 PNG 逐字节一致。这是单机固定回放的差值，不代表生产负载。
- 问：恢复后的运行怎样计分？
  答：续跑按连续运行统计，动作数和预算延续；改了辅助或策略的续跑单独列出，不并入原样本。

## 03 · VISTA 实例｜框架优化：11 项 aids

### 第 21 页 · 11 项 aids：把执行历史整理成决策提示

约 100 秒 · 累计 33:05–34:45

11 项 aids 来自 Luna、DS、GLM 轨迹中反复出现的失败，例如漏读反馈、重复失败的实验、误解预算、丢失规则、误读坐标和交接不足，表中按用途分四类。

观测解码有四项：diff 比较动作前后的画面，geometry 说明网格坐标，click 回显点中的对象，layout 在新关卡列出对象。检索、统计与停滞有四项：repeat 检索相似局面过去的动作和结局，coverage 统计点击覆盖，attempt 汇总尝试的动作数和结果条件，stall 在画面停滞时要求更新笔记。记忆与交接有两项：mechanisms 记录带证据回合的规则，可以修订和撤回；handoff 按局面、模型、已试、计划和未决问题写交接。最后是 reset，允许重开本关来重新验证假设。

统计由确定性代码维护，规则由模型编写，框架保存证据和修订；辅助只使用运行中可见的信息，游戏源码只用于事后核验。得分对应 11 项的组合，单项贡献需要消融实验。

## 03 · VISTA 实例｜整体结果

### 第 24 页 · Luna：完整框架与经验辅助的整体效果

## Trace：是什么、存什么、怎么存、怎么用

### 第 25 页 · Trace：是什么、存什么、怎么存、怎么用

约 50 秒 · 累计 39:45–40:35

最后按四个问题总结。Trace 是一次运行的 span 树，记录父子关系、时间、状态和类型，可以由它还原对话文本、重放 state、提炼 memory。存什么：按 GenAI 约定，结构与时间必有，属性可选，内容体积大、默认不采集。

怎么存：动态属性按查询形态选 JSON 表示，长载荷按引擎选同表、列表副本或外置。怎么用：在 VISTA 中支持读回历史、断点恢复和经验提示，事后用于评估、数据准备和失败归因。失败归因由下一位同事介绍。
